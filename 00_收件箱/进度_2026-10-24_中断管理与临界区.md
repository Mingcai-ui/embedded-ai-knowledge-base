## 一、学了什么

### 1. TIM 中断链路：从配置到触发（缺的那一步）

`MX_TIM1_Init()` 只写寄存器配置（PSC / ARR / NVIC），**不置 CR1.CEN，也不置 DIER.UIE**。

中断真正生效需要三件事同时成立：

| 条件 | 谁来置 | CubeMX 代码里有吗 |
| --- | --- | --- |
| NVIC 通道使能 | `HAL_NVIC_EnableIRQ()` | ✅ `HAL_TIM_Base_MspInit` 里有 |
| 外设中断使能位 DIER | `__HAL_TIM_ENABLE_IT()` | ❌ 没有 |
| 计数器启动 CR1.CEN | `__HAL_TIM_ENABLE()` | ❌ 没有 |

所以必须补一行 `HAL_TIM_Base_Start_IT(&htim1);`。缺这一步的表现是：ISR 写对了、`extern` 写对了、回调写对了，但**中断永远不触发**。

补充两条：
- TIM1 是高级定时器，做**更新中断**不需要 MOE（`__HAL_TIM_ENABLE_MOE`），只有输出比较 / PWM 才要。
- 周期公式：`T = (PSC+1) × (ARR+1) / 72MHz`。PSC=7199、ARR=9999 → 1s。ARR=65535 时是 6.55s，看着像"没反应"。

#### 1.1 `HAL_TIM_Base_MspInit` / `MspDeInit` 与 `MX_TIM1_Init` 的分工

翻底层翻到的那两个函数，是**板级初始化**，和定时器本体配置分工明确：

```c
void HAL_TIM_Base_MspInit(TIM_HandleTypeDef* tim_baseHandle)
{
  if(tim_baseHandle->Instance==TIM1)
  {
    __HAL_RCC_TIM1_CLK_ENABLE();              // 外设时钟
    HAL_NVIC_SetPriority(TIM1_UP_IRQn, 5, 0); // 抢占优先级 5，子优先级 0
    HAL_NVIC_EnableIRQ(TIM1_UP_IRQn);         // 打开 NVIC 通道
  }
}

void HAL_TIM_Base_MspDeInit(TIM_HandleTypeDef* tim_baseHandle)
{
  if(tim_baseHandle->Instance==TIM1)
  {
    __HAL_RCC_TIM1_CLK_DISABLE();             // 反初始化时关时钟（省电）
    HAL_NVIC_DisableIRQ(TIM1_UP_IRQn);        // 关 NVIC 通道
  }
}
```

| 函数 | 管什么 | 谁调用 |
| --- | --- | --- |
| `MX_TIM1_Init()` | PSC / ARR / 计数模式 / 触发源（**定时器本体**） | `main()` 显式调用 |
| `HAL_TIM_Base_MspInit()` | 时钟使能、NVIC 优先级与使能、DMA（**板级资源**） | HAL 在 `HAL_TIM_Base_Init()` 内部回调，看不到显式调用 |
| `HAL_TIM_Base_MspDeInit()` | 关时钟、关 NVIC | `HAL_TIM_Base_DeInit()` 时回调 |

三个要点：

1. **`Msp` = MCU Support Package**。CubeMX 把"芯片无关的配置"和"芯片相关/板级相关"分开，Msp 是后者。
2. **NVIC 使能在这里，不在 `MX_TIM1_Init` 里**。所谓"中断配置好了"，其实是 MspInit 干的。
3. **按实例分流**（`if(tim_baseHandle->Instance==TIM1)`），所以一个文件能同时服务 TIM1/TIM2/TIM3，加定时器不会互相覆盖。

⚠️ 实践提醒：如果你在 `USER CODE` 区自己重写一份 `HAL_TIM_Base_MspInit`，会和 CubeMX 生成的那份冲突（重复定义或只留你的那份），**时钟和 NVIC 会全部失效**——表现和"忘了 Start_IT"一模一样。Msp 区一般不要碰。

#### 1.2 跟着教程写的一层多余封装：`HAL_TIM_INT_IRQHandle`

跟着正点原子视频写的：

```c
void HAL_TIM_INT_IRQHandle(void)
{
  HAL_TIM_IRQHandler(&htim1);   // 定时器回调函数
}
```

他自己对这个函数的理解是**对的**：中断触发 → CPU 进 `HAL_TIM_INT_IRQHandle` → 调 `HAL_TIM_IRQHandler` → 后者分发到 `HAL_TIM_PeriodElapsedCallback`。

问题不在理解，在这层封装**在 CubeMX 工程里是多余的**：

1. **这个名字不是 HAL 官方的**。官方只有 `HAL_TIM_IRQHandler(TIM_HandleTypeDef *htim)`，**带参数**。
2. **正点原子的用法成立，是因为他的 `stm32f1xx_it.c` 里写的是 `HAL_TIM_INT_IRQHandle();`**（纯手写工程，`it.c` 由他自己维护）。
3. **本项目不行**：CubeMX 生成的 `stm32f1xx_it.c` 里是 `TIM1_UP_IRQHandler() → HAL_TIM_IRQHandler(&htim1)`，已经直连。再补一层没有调用者。
4. 当时这段放在 `tim.c` 的 `USER CODE BEGIN 1` 里且**是注释掉的**，所以没造成故障；即使启用，也只会多一个 `unused function` 警告。

**教训**：照抄教程代码前，先确认"教程的 `it.c` 是谁维护的"。手写工程和 CubeMX 工程的中断入口归属不同，同一个封装在两边一个是必需、一个是废码。

正确的链路只有下面这一条，**不要自己加第三层**：

```
启动：   HAL_TIM_Base_Start_IT(&htim1)
           └→ __HAL_TIM_ENABLE_IT(IT_UPDATE)  +  __HAL_TIM_ENABLE(CEN=1)

中断：   TIM1_UP_IRQHandler()                 [stm32f1xx_it.c，CubeMX 管的]
           └→ HAL_TIM_IRQHandler(&htim1)      [HAL 库，清标志 + 分发]
                └→ HAL_TIM_PeriodElapsedCallback(htim)   [main.c，你写业务]
```

判断标准就一条：**业务代码只应出现在 `HAL_TIM_PeriodElapsedCallback` 里**。ISR 入口和分发都在库和 CubeMX 手里。

### 2. "关中断"有四个层级，作用范围完全不同

| 层级 | 函数 | 影响范围 | 可嵌套 |
| --- | --- | --- | --- |
| 全局 PRIMASK | `__disable_irq()` / `__enable_irq()` | 全部可屏蔽中断，含 prio 0 | ❌ |
| NVIC 通道 | `HAL_NVIC_DisableIRQ()` / `EnableIRQ()` | 单条中断线（标志位仍会置） | — |
| 外设使能位 | `__HAL_TIM_DISABLE_IT()` / `HAL_TIM_Base_Stop_IT()` | 单个外设的某类事件 | — |
| RTOS 临界区 | `taskENTER_CRITICAL()` / `EXIT` | prio ≥ configMAX_SYSCALL(5) | ✅ |

注意 `osKernelLock()` **不是关中断**，它只锁调度器。

### 3. `portDISABLE_INTERRUPTS()` 的真实语义

本工程实际展开（`portmacro.h:101`）：

```c
#define portDISABLE_INTERRUPTS()   vPortRaiseBASEPRI()   // msr basepri, 0x50
#define portENABLE_INTERRUPTS()    vPortSetBASEPRI(0)    // msr basepri, 0
```

`0x50 = 5 << 4`，来自 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`。

三条关键认知：
1. **不是"全关"，是按优先级屏蔽**：prio 5~15 被挡，prio 0~4 照跑。
2. **`portENABLE_INTERRUPTS()` 无条件写 0**，不保存旧值、无嵌套计数。嵌套两次 disable 只 enable 一次，会把中断全开，破坏内核自己的临界区。
3. **`taskENTER_CRITICAL()` = 同一动作 + `uxCriticalNesting` 计数**，所以应用代码一律用它。

### 4. `HAL_Delay` 在关中断下会永久死锁（本次核心）

错误写法：

```c
portDISABLE_INTERRUPTS();   // basepri = 0x50
HAL_Delay(5000);            // ← 死在这里
portENABLE_INTERRUPTS();    // ← 永远执行不到
```

因果链：

```
HAL_Delay 等 uwTick 变量
  → uwTick 由 HAL_IncTick() 在 TIM4_IRQHandler 里递增
  → TIM4 优先级 15，被 BASEPRI=0x50 屏蔽
  → uwTick 永久冻结，while 差值恒为 0
  → 死循环，ENABLE 永不执行
```

**为什么正点原子同样的代码能跑**：他的 `delay_ms` → `delay_us` 是**轮询 `SysTick->VAL` 寄存器**。

一句话区分：**"等变量"依赖中断，"查硬件计数器"不依赖。** SysTick 的计数器在关中断时依然递减，只是它的中断响应被屏蔽。这是全篇最有价值的一条。

修复方案：自写 `delay_us_noint()` 轮询 `SysTick->VAL`（含递减回绕补偿），已在工程里实现并编译通过。

### 5. 任务调度同样被掐断，而且是两级

| 层级 | 异常 | 优先级 | 被屏蔽后 |
| --- | --- | --- | --- |
| ① 请求 | SysTick | 15 | `xTaskIncrementTick()` 不跑，`xTickCount` 不增 |
| ② 执行 | PendSV | 15 | 即使挂起位已置，异常不响应，不切栈 |

**PendSV 为什么存在**：可挂起（写 `ICSR.PENDSVSET` 即请求，不必立刻执行）+ 必须最低优先级，保证所有中断处理完才切栈。若在 SysTick 里直接切，遇到嵌套中断时会切在错误的栈帧上。

一条可实测的细节：临界区内 `taskYIELD()` 只置 `ICSR.PENDSVSET`，任务**不会**当场切换，要到 `portENABLE_INTERRUPTS()` 执行完的那一瞬间才切。

由此推出两条铁律：

1. **临界区禁止一切阻塞 API**（`osDelay` / `osMessageQueueGet` / `osMutexAcquire`）。它们靠 PendSV 把任务切走，PendSV 被屏蔽 → 函数返回后"已阻塞"的任务继续跑 → 链表错乱。**这类 bug 不会当场报错，事后才崩，最难查。**
2. **`FromISR` 的 prio ≥ 5 限制和 BASEPRI 是同一套机制**。prio 0~4 里调内核 API，内核想用 BASEPRI 保护自己也保护不住。

## 二、踩过的坑（四个真实故障）

体例同 [[FreeRTOS_阶段一故障合集]]：现象 / 根因 / 解决，按现象可检索。

| # | 坑 | 现象 | 根因 | 解决 |
| --- | --- | --- | --- | --- |
| 1 | 只 `Init` 不 `Start_IT` | 中断线、`extern`、回调全写对了，LED 就是不动 | `MX_TIM1_Init` 不置 `CR1.CEN`、不置 `DIER.UIE` | 补 `HAL_TIM_Base_Start_IT(&htim1)` |
| 2 | ARR 用了默认 65535 | 加了启动还是"不闪"，一度怀疑没烧进去 | 72MHz ÷ 7200 ÷ 65536 = 6.55s 才翻一次 | ARR 改 9999 → 1s |
| 3 | `HAL_Delay` 夹在关中断里 | 关中断后 LED **永久**停，不是 5 秒后恢复 | `uwTick` 靠 TIM4 中断（prio 15）递增，被 BASEPRI 屏蔽 → `while` 死循环 → `ENABLE` 永不执行 | 改用轮询 `SysTick->VAL` 的 `delay_us_noint()` |
| 4 | 以为 `portDISABLE_INTERRUPTS()` 是"关全部中断" | 无法解释为什么正点原子同样的代码能跑 | 它是 `msr basepri, 0x50`，只屏蔽 prio ≥ 5 | 认清优先级数值 + 做对照实验（TODO） |

**坑 3 是本次最值钱的一个**，完整因果链见 §4。一句话记忆点：

> `HAL_Delay` 等的是**变量**（`uwTick`，靠中断喂），`delay_us` 查的是**硬件计数器**（`SysTick->VAL`，关中断照跑）。

**坑 1 和坑 2 的组合最坑人**：两个都修好之前，任何一次"改了没效果"都会让你误判。排查顺序应该是「先确认 `HAL_TIM_Base_Start_IT` 在不在 → 再算 ARR 是否合理 → 再怀疑中断优先级」。

**坑 4 的教训**：`portDISABLE_INTERRUPTS()` / `portENABLE_INTERRUPTS()` 无嵌套计数，`ENABLE` 是无条件 `basepri = 0`。工程代码一律用 `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`。

### 预判坑（调研得出，尚未亲自踩）

`printf` 部分虽然没动手，但已经能提前列出五个坑，省得以后一个个撞：

1. 照抄 Keil 的 `int fputc(int ch, FILE *f)` —— GCC/newlib 走的是 `_write`，改了完全不生效。
2. 直接改 `syscalls.c` 里的 `_write` —— CubeMX 重新生成会还原，改动丢失。正确做法是在自己 .c 里给强定义（原函数已是 `weak`）。
3. 只写 `\n` —— GCC 不补 `\r`，串口助手出现阶梯式错行。
4. `defaultTask` 栈 512 B 就上 `printf` —— 栈溢出，表现为 HardFault 或莫名重启。
5. `%f` 打不出来 —— newlib-nano 裁剪了浮点格式化，链接要加 `-u _printf_float`。

### 本次被纠正的三条认知（重要，比坑更值钱）

> 2026-10-24 20:23 十六题答辩中暴露，均为"理解了但有偏差"。

**1. `portDISABLE_INTERRUPTS` 不是"只能调用一次"，是"没有计数"**

初始表述为"只能调用一次"。追问后本人自行修正为："嵌套时第二次关闭基本等于没运行，第一次恢复就完全恢复了" —— **修正正确**。

准确说法：它无判断、无计数，**嵌套等于失效**。内层 `disable` 是空操作，内层 `enable` 会把中断**提前全开**，外层临界区从这一刻起形同虚设。所谓"只能调用一次"容易误解成"调用两次会崩"，其实是"第二次不起作用，且会让第一次失效"。

**2. `osDelay` 和 `HAL_Delay` 不是同一个机制**

原先理解为"两个都是定时器计数，关中断后都失效"。实际两者失效**表现相似、机理相反**：

| | `HAL_Delay` | `osDelay` |
| --- | --- | --- |
| 本质 | **忙等变量** `uwTick` | **阻塞任务**等 tick |
| 关中断后 | `while` 死循环，**CPU 空转跑飞** | 任务永不被唤醒，**静默卡在阻塞态** |
| 谁在消耗 CPU | 是 | 否（让出了 CPU） |
| 表现 | 现场还能被调试器打断在循环里 | 系统看起来"正常"但任务再不动 |

这个区别决定了出问题时该看"CPU 在跑什么"还是"任务在哪个状态"。

**3. "临界区不能用 `osDelay`，只能用自己写的 Delay"是错的**

出自正点原子视频，但这句话**危险**。自己写的轮询型 Delay 确实不会死锁，但它把**关中断时间拉长到毫秒级**，比"一眼看出来卡死"更隐蔽地破坏系统实时性。

正确原则：**临界区里根本不该有任何延时** —— `osDelay`、`HAL_Delay`、自己写的 Delay 一律不行。临界区的唯一任务是保护几条指令的原子性。

### 7.2 实验 1：断点命中回调

断点下在 `main.c:168 HAL_TIM_PeriodElapsedCallback`，F5 后停住 → **证明 TIM1 中断链路真的在跑**（10-24 那个"LED 不反转"的证据链至此闭环）。

继续用 F11 单步，走出这样一条路径：

```
HAL_TIM_PeriodElapsedCallback   main.c:168
  → HAL_GPIO_TogglePin          stm32f1xx_hal_gpio.c:487
  → 回到 HAL_TIM_IRQHandler
  → if ((itflag & TIM_FLAG_BREAK) == TIM_FLAG_BREAK)   stm32f1xx_hal_tim.c:3964
```

### 7.3 这条路径带出的四件事

#### (1) `HAL_TIM_IRQHandler` 是"一个入口，轮询所有标志"

不是 `else if`，是 8 个独立 `if`，每个都做**双层判断**：

```c
uint32_t itsource = htim->Instance->DIER;   // 哪些中断被使能
uint32_t itflag   = htim->Instance->SR;     // 哪些标志置位

if (事件发生了 && 中断被使能了) { 清标志; 调回调; }
```

| 行号 | 分支 | 备注 |
| --- | --- | --- |
| 3828 | CC1 | |
| ~3840 | CC2 / CC3 / CC4 | |
| **3951** | **UPDATE** | **业务回调在这里被调用** |
| **3964** | **BREAK** | 高级定时器独有；未接刹车引脚则恒为 0 |
| 3977 | TRIGGER | |
| 3990 | COM | |

所以 UPDATE 处理完**不返回**，继续往下检查。看到 `TIM_FLAG_BREAK` 那行不是出错，是顺序走过去了。

代价：每次中断把 8 个标志全查一遍，几十条指令。高频中断场景有人因此绕开 HAL 手写 `IRQHandler`。

#### (2) 变量是快照，寄存器是实时值

停在 3964 行时：

| 看什么 | 值 | 原因 |
| --- | --- | --- |
| 局部变量 `itflag` | `0x0001` | 进函数时对 SR 的快照 |
| 硬件 `TIM1->SR` | `UIF = 0` | 3955 行 `__HAL_TIM_CLEAR_FLAG` 已清过 |

**查"标志位一直置着不清"的 bug，要读寄存器，不能只看变量。**

#### (3) `HAL_GPIO_TogglePin` 用一次 BSRR 写完成翻转

```c
odr = GPIOx->ODR;
GPIOx->BSRR = ((odr & GPIO_Pin) << 16)    // 当前为 1 的位 → 高 16 位 = 复位
            | (~odr & GPIO_Pin);          // 当前为 0 的位 → 低 16 位 = 置位
```

BSRR 低 16 位写 1 = 置位，高 16 位写 1 = 复位 → **一次写操作同时完成"该置的置、该复的复"**，原子，不存在"先清后置"的中间态。比 `if(ReadPin) WritePin(RESET) else WritePin(SET)` 那种读-改-写安全。

#### (4) F10 / F11 / Shift+F11 的分工

| 键 | 行为 | 什么时候用 |
| --- | --- | --- |
| **F10** 单步跳过 | 整个函数当一条指令 | 看自己的逻辑（**默认键，90% 场景**） |
| F11 单步进入 | 钻进函数第一行 | 专门要看库内部 |
| Shift+F11 单步跳出 | 跑完当前函数立刻返回 | 进错了赶紧出来 |

首次实操全程默认按 F11，属于拿"钻"当"走"。**要刻意练 F10。**

### 7.4 实验 2：用调试器实测堆大小

顺着 `osThreadNew` 一路 F11 钻进去，抓到了完整的三层调用链：

```

MX_FREERTOS_Init    freertos.c:115
osThreadNew         cmsis_os2.c:501       ← 自己写的 CMSIS-OS2 层
```

| 观测 | 值 | 意义 |
| --- | --- | --- |
| `xTotalHeapSize` | **3072** | 本工程 `configTOTAL_HEAP_SIZE` 仍是 3072（阶段一记录的 3072→10240 是另一个工程）。**printf 之前必须先扩堆 —— 这次是实测，不是推测** |
| `prvHeapInit` | 只在**第一次** `pvPortMalloc` 时执行 | 初始化空闲链表头 `xStart` 与尾哨兵 `pxEnd`，之后整个生命周期不再进入 |

| 占用 | 大小 |
| --- | --- |

| idle task 栈 | 512 B |

| 3 个 TCB | ~270 B |
| timer queue（10 项） | ~160 B |
| **合计 / 余量** | **~2480 / ~600 B** |

### 7.5 `<optimized out>` 的正确判断

停在 `heap_4.c:341`（`uxAddress = (size_t)ucHeap;`）时，`uxAddress` / `pucAlignedHeap` / `pxFirstFreeBlk` 全显示 `<optimized out>`，而 `xTotalHeapSize` 显示 3072。

**两个原因叠加：**

1. **GDB 箭头指向"即将执行的下一行"** → 341 行还没跑，变量自然空；338 行的 `xTotalHeapSize = configTOTAL_HEAP_SIZE;` 已执行，所以看得到 3072
2. `-Og`（EIDE 的 `optimization: level-debug`）下，无稳定栈位置的临时变量被报告为 optimized out

**判断法**：按一次 F10，变量冒出数值 → 只是"还没执行到"；走完整函数仍是 `<optimized out>` → 才是被优化掉。
