## 一、原理层

- 网络课学过的**模 2 除法**与代码里的**移位寄存器（LFSR）**是同一件事的两种视角。
- 网络课算法必须拿到完整数据块才能算；嵌入式要流式处理，改为从最低位逐位消去。
- 为保持等价，全部参数镜像翻转：多项式 `0x8005 → 0xA001`，输入/输出位序也翻转。
- `RefIn=true / RefOut=true` 不是特性，是镜像后必然留下的记录。

### 参数层

| 参数 | 值 |
|---|---|
| Poly | 0x8005（算法里用反转值 0xA001） |
| Init | 0xFFFF |
| RefIn / RefOut | true / true |
| XorOut | 0x0000（Modbus 不做最终取反） |
| 标准校验值 | `"123456789"` → 0x4B37 |

## 二、手算验证（已完成）

完整手算了 `11 03 00 6B 00 03`（规范原文示例）6 个字节全流程，结果 **0x8776**，与规范一致。

规范原文对照：

```
请求：11 03 00 6B 00 03 76 87
应答：11 03 06 AE 41 56 52 43 40 49 AD
```

两帧均已复算确认（请求 CRC 0x8776，应答 CRC 0xAD49）。

## 三、关键认知修正

### 1. 多项式只有三个位会翻转

`0xA001` = `1010 0000 0000 0001`，异或时只影响 **bit15、bit13、bit0**，其余 13 位不动。
自查判据：算完一步若发现被翻转的位不止这三个，一定是多项式写错了。

本次实际踩到：手算第 5 个字节时，异或运算把高 8 位中不该动的四位写反，导致结果偏移。自己定位出错误位并修正。

### 2. 帧长由协议规定，不能截断

功能码 03 请求固定 6 字节（地址 1 + 功能码 1 + 起始地址 2 + 数量 2）+ CRC 2 = 8 字节。
本次曾按 4 字节、5 字节分别计算，得到 0xF7B4、0x77F7，均为无效值。
**CRC 验证的方向是"给定完整帧查结果"，不是"从 CRC 反推帧长"。**

### 3. AI 不能作为 CRC 计算基准

实测：DeepSeek 对 `11 03 00 6B 00 03` 给出 0x683B，错误，且无法对应任何常见变体（已排除 MODBUS / ARC / 非反射 0x8005 四种参数组合）。
原因：LLM 是在"生成数字"而非"执行算法"，48 次条件移位无法靠模式匹配推对。

基准只认两个：
- 协议规范原文的示例帧
- 在线工具 crccalc.com，必须选 `CRC-16/MODBUS`（不是 ARC）

### 4. 调试顺序

值不对时按序查：输入（字节数/漏字段）→ 参数（Init/Poly/XorOut）→ 字节序（低字节先）→ 实现（移位次数）。
本次属于第 0 类：输入不完整。若跳过第 0 步直接改算法，会越改越错。

## 四、实现方法分类（认知修正）

此前认为 `Core/Src/CRC16.c` 里的实现属"查表法"，**错**。

| 名称 | 别名 | 判据 |
|---|---|---|
| 逐位法 | bit-by-bit / 位运算法 | 双层循环，每字节跑 8 次移位判断 |
| 半字节表法 | nibble table | 16 项常数表（32 B Flash），每字节查 2 次 |
| 全字节表法 | byte table | 256 项常数表（512 B Flash），每字节查 1 次 |

**判据一句话：代码里有没有 `static const uint16_t table[...]`。有表才是查表法，没有就是逐位法。**

当前实现是标准的逐位法，无表、无 Flash 开销。全字节表法也只停留在能读懂、未自行推导 `(crc>>8) ^ table[(crc^byte)&0xFF]` 的由来。

## 五、STM32F103 硬件 CRC 单元的能力边界

F1 的 CRC 单元**完全不可配置**：寄存器只有 `CRC_DR`（数据/结果）、`CRC_IDR`（8 位独立寄存器）、`CRC_CR`（仅 `RESET` 位）。

| 项 | F1 硬件 CRC | CRC-16/Modbus 需要 | 是否匹配 |
|---|---|---|---|
| 位宽 | 32 | 16 | ✗ |
| 多项式 | 0x04C11DB7（固定，不可写） | 0x8005 | ✗ |
| 输入/输出反射 | 无 | 有 | ✗ |
| 初值 | 0xFFFFFFFF | 0xFFFF | ✗ |
| 最终异或 | 0 | 0 | ✓ |

四处里三处不匹配，**位宽是硬伤**——32 位结果无法映射回 16 位校验值，不是"包装一下"能解决的。

F1 硬件 CRC 唯一对应的标准变体：**CRC-32/MPEG-2**（已用逐字节模型验证 `"123456789"` → `0x0376E6E7`，与标准 check 一致）。

另有一个实操障碍：硬件按 **32 位字** 写入，Modbus 帧长 8/11/255 字节都不是 4 的倍数，尾部需软件特殊处理（补 0 会改结果，已验：补 3 字节 0 后 `AE24E09D` ≠ check 值）。

> F4/F7/L4 的 CRC 单元有 `CRC_POL` 可写 + `REV_IN`/`REV_OUT`，理论上能配成 CRC-16/Modbus。**F1 没有这些位**，换芯片才有这条路。

## 六、"省 CPU"在本场景是伪需求（量化）

72 MHz Cortex-M3，256 字节（Modbus RTU 单帧上限）：

| 方法 | 单帧耗时（估算） | 9600 bps 传输 256 B = 267 ms 占比 |
|---|---|---|
| 逐位法 | ~200 µs | 0.07 % |
| 全字节表法 | ~40 µs | 0.015 % |

115200 bps 下 256 B = 22 ms，逐位法仍只占 0.9 %。

**结论：单帧 CRC 在 Modbus 场景永远不是瓶颈，省下来的是 0.06 % 的 CPU，代价是 512 B Flash 和一张需要维护的表。** 逐位法在此场景是正确选择，不是"没优化的版本"。

真正值得上硬件 CRC 的场景：OTA 固件整片校验（1 MB → 表法 ~150 ms，硬件 ~1 ms）。届时 P0 已结束，属另一课题。

## 八、反向校验字节序（易踩坑，务必记住）

2026-11-01 修正：应答帧 `11 03 06 AE 41 56 52 43 40 49 AD` 的 CRC 值为 **0xAD49**，Modbus 低字节先发，帧内顺序是 **`49 AD`**。

> ⚠️ 若把末两字节写成 `AD 49`（高字节先），反向校验结果是 `0x4B4B` 而非 0，会误判成算法错。
> 反向校验必须**按发送顺序**追加才归零。这是字节序坑，不是算法坑。

### 短板

- **手算精度**：48 次条件移位手算易错。手算只做一次建立位级直觉，此后一律用代码 + 规范原文对照。
- **状态机仍是最大缺口**：CRC 属"有明确算法可对照"的题，状态机属"无标准答案、靠设计能力"的题，后者才是 P1 的真正门槛。
- **未建立"先量化后优化"的默认反射**：本次先有"用硬件省算力"直觉，再回头算占比发现不成立。正确顺序是先算占比，占比 < 1 % 就不看优化方案。
- **查表法的原理层缺口**：会背结论，讲不清"表项本质是 8 位输入对应的 8 次移位结果"，属知其然。
- **易被"外设能加速"的直觉带偏**：外设是否适用取决于参数匹配而非外设存在，判据固定在"对照参数表"。
- **AI 依赖风险已实证**：AI 在纯计算结果上给出错误答案且无自检能力。验收标准必须落在可执行的对照物上（规范 / 工具 / 实测），不能落在"AI 说对"。
