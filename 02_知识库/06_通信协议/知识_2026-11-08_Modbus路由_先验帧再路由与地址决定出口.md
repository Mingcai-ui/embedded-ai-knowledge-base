# Modbus 路由器：先验帧再路由 + 地址决定出口（2026-11-08）

> 把 PC 侧从「收到什么都转发」的裸透传桥，升级成带身份判断的路由器。
> 对应 `feat/modbus-router` 分支的 `uartDataHandler_PC()` 与 `sendMessage()`。
> 记录的是实现思路与踩坑，属自己手写、AI 审校的代码。

## 1. 一句话定位

PC 发来的 Modbus 请求，先**验帧**（长度 + CRC）、再**看地址**、最后决定归谁处理：

- `0x01` → 原样透传给 RS485 外部温湿度变送器，由它自己应答
- `0x02` → 本机 DHT11 虚拟从机，读缓存组帧后从 USART1 直接回 PC
- 其他 → 静默丢弃 + 计数

## 2. 四个核心设计

### 2.1 先验帧再路由（checkFrame）

坏帧在路由前就被拦下，不占用 RS485 总线和变送器的处理时间。`checkFrame()` 只做两件事：

- 长度 < 4 → `FRAME_Too_SHORT`
- CRC 不对 → `FRAME_CRC_ERR`

**上界不在这里判**：`len` 是 uint8_t，接收中断已在 `BUFFERSIZE` 处封顶，函数根本看不到「超长」。
所以「超长」这件事只能由中断标志折算（见 2.3）。

### 2.2 地址决定出口（sendMessage）

`sendMessage()` 看帧头第一个字节选物理链路：

```c
if (msg[0] == SLAVEID) {          /* 0x01 → USART2 + 拉高 DE */
    rs485Mode(1);
    HAL_UART_Transmit(&huart2, msg, len, len*2+10);
    rs485Mode(0);
} else {                          /* 其他 → USART1 回 PC，不碰 DE */
    HAL_UART_Transmit(&huart1, msg, len, len*2+10);
}
```

因为 Modbus 帧头第一个字节就是从机地址，这个判断天然成立。好处是 `makePacket_01/03/05/06/15/16`
和 `sendException` **一行不改**，全部自动获得「按地址选出口」的能力。

**这是本次最省事的解法**：改一个函数，让整条应答路径（含异常响应）都能走对出口。
关键前提是「帧头地址 == 物理出口的判别条件」恰好一致。

### 2.3 超长 vs 正好 255 字节合法帧（frameOverflow_PC）

`DataCounter_PC` 停在 255 时，主循环分不清「正好 255 字节的合法长帧」和「256 字节的超长帧」——
两者的计数器数值一样。这个事实**只有中断知道**（第 256 个字节到了才会走 `else`），
所以由接收中断置 `frameOverflow_PC`，主循环 `uartDataHandler_PC()` 取走并清零，折成 `FRAME_Too_LONG`。

`BUFFERSIZE=255` 恰好 = 0x10 写满 123 寄存器的 ADU 上限（1+1+2+2+1+246+2=255），
**不可升 256**，否则 uint8_t 计数器回绕成 0、整帧被当空帧丢弃。

### 2.4 溢出标志跨帧残留

`HAL_UART_ErrorCallback` 清 `RxInterruptFlag_PC=RESET` 后，定时器不再判帧、handler 不执行；
若此刻 `frameOverflow_PC` 仍是 SET，会**残留到下一帧**，把一条完全合法的请求误判成 `FRAME_Too_LONG`。

故障链：256 字节帧置 SET → 同帧 ORE 进错误回调 → 标志被清 → handler 永不跑 → SET 残留 →
下一帧合法请求被判超长。修法：错误回调里一并清 `frameOverflow_PC`。

## 3. 四个丢弃计数器（分开记才有诊断价值）

| 计数器 | 含义 |
|---|---|
| `bad_SHORT` | 帧长 < 4：判帧阈值或链路问题 |
| `bad_LONG` | 超长（由 `frameOverflow_PC` 折算） |
| `bad_CRC` | CRC 错：帧内容坏了 |
| `bad_Addrs` | 地址既非 0x01 也非 0x02 |

四个分开记，是因为它们指向完全不同的故障源；混成一个「丢弃计数」就失去了诊断价值。

## 4. 02 从机的两个约束

- **只读 0x03**：其余功能码回异常 `0x01`。因为写进去的值会被下一次 2s 采样直接覆盖，
  开放写会让 PC 误以为写入成功，反而比直接拒绝更难排查。
- **采样只在总线静默时做**：`DHT11_ReadFrame()` 内部关中断约 4ms，主循环判断
  `RxInterruptFlag_PC` 与 `RxInterruptFlag` 都静默才驱动传感器，把这段 4ms 挪到总线空闲缝隙，
  避免顶掉 PC 帧。采样与调试打印也已解耦（`DHT11_Handler` 在 `#if` 之外无条件跑）。

## 5. 测试帧（Python 独立算过 CRC）

| 请求 | 应答 | 含义 |
|---|---|---|
| `02 03 00 00 00 02 C4 38` | `02 03 04 01 13 02 4E B8 5E` | 27.5℃ / 59.0%RH（寄存器 0=温度×10、1=湿度×10） |
| `02 03 00 09 00 04 <CRC>` | `02 83 02 30 F1` | 起始 9 + 4 > 10，越界 → 异常 0x02 |
| `02 06 00 00 00 64 <CRC>` | `02 86 01 <CRC>` | 02 只读，写请求 → 异常 0x01 |

## 6. 待办 / 已知限制

- **02 端到端未上板实测**；01 透传因 `sendMessage` 是共享函数，改动后需回归复测。
- **无请求—应答状态机**：PC 帧到达即转发，不判断总线忙、不排队、不限速。高速请求下
  变送器应答会被腰斩（16ms 连发复现），根治需 `IDLE → SENDING → WAIT_RESP → IDLE`。
- **拆包不重组**：Modbus RTU 无长度字段，帧边界靠静默间隔；根治需按功能码「长度字段提前判帧」。
