# 工作流：日记流转（生成 → 整理 → 推送 → 归档）

四层流水线：每天用便宜模型做机械转换，每周用强模型做判断归档。
核心原则：**日记是唯一原始输入；Flash 只格式化不判断；Max 只判断不高频。**

| 阶段 | 工具 | 频率 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| 1 生成 | WorkBuddy + DeepSeek Flash/Pro | 每次会话结束 | 会话上下文 | `00_收件箱/日记_*.md` |
| 2 整理 | Trae + Qwen Flash | 每天 | 日记 | 收件箱内的正式笔记草稿 |
| 3 推送 | Trae + Qwen Flash | 每天 | 日记代码变更字段 | git commit；里程碑时更新 README |
| 4 归档 | Qwen Max | 每周 | 收件箱全部草稿 | 归位到 01/02/09 等 + 收件箱清零 |

## 阶段 1：生成日记（WorkBuddy + DeepSeek）

会话结束时把 [[模板_日记]] 贴给 WorkBuddy，要求：

> 根据本次会话内容填写模板_日记。一个独立任务一个任务块；字段填不出写「无」，
> 不许省略字段；「做了什么」动词开头；「坑」必须包含现象；
> 有截图/波形/日志就写进「证据」并说明存放位置。

规则：
- 日记存入 `00_收件箱/`，命名 `日记_YYYY-MM-DD_主题.md`。
- 证据文件（截图 / 波形）同步放入 `assets/` 或对应仓库的 `docs/`，日记里写路径。

## 阶段 2：日记 → 收件箱正式笔记（Trae + Qwen Flash）

Flash 只做**格式转换**，不做归位判断。提示词：

> 读取 00_收件箱/日记_*.md，把每个任务块拆成独立笔记，仍放在 00_收件箱/：
> 1. 「坑」且原因已定位 → 按 07_模板/模板_排坑 生成，命名参照 09_排坑 现有风格
>    （现象关键词_原因关键词.md），frontmatter 类型: 排坑。
> 2. 「学到的概念」→ 按 模板_知识 生成，命名用正名词组，类型: 知识。
> 3. 项目进展（做了什么 + 遗留问题）→ 追加到 01_项目/ 对应项目笔记；
>    项目笔记不存在时按 模板_项目 新建。
> 4. 遵守 AI导航.md 第 2 节 frontmatter 契约：中文键，类型只取 13 个合法值，
>    创建 填今天。不许移动文件到 00_收件箱 以外，不许自造类型。
> 5. 处理完在日记文件末尾追加一行 `已整理: YYYY-MM-DD`。

## 阶段 3：GitHub 提交与项目介绍（Trae + Qwen Flash）

**每日提交**（治"做完一次性上传"）：

> 根据日记的「代码变更」字段为每个仓库生成 commit message 并提交推送：
> 格式 `<type>(<scope>): <中文描述>`，type 取 feat/fix/docs/refactor/test；
> 一个任务块一个 commit，不要把多个任务块合并成一条。

**README 只在里程碑更新**（任务块「里程碑 = 是」时）：

> 该任务块完成了 <功能>。请更新仓库 README：只改「功能列表 / 完成度 / 用法」
> 中与本功能直接相关的段落，给出 diff 让我确认后再提交；
> 不许重写无关段落，不许删除「进行中 / 待实现」清单里尚未完成的条目。

规则：
- 非里程碑日**不碰** README，只提交代码。
- README 的 diff 必须人工确认后才推送（防幻觉改坏项目介绍）。
- 证据（波形截图 / 日志）随里程碑一并提交到仓库 `docs/`。

## 阶段 4：每周归档（Qwen Max）

每周一次，提示词：

> 执行知识库周归档：
> 1. 收件箱清零：把 00_收件箱/ 中带「已整理」标记的笔记归位——
>    排坑 → 09_排坑/；知识 → 02_知识库/ 对应子分类；项目类 → 01_项目/；
>    原始日记移入 08_归档/。归位前先查目标目录有没有同主题笔记，
>    有则合并而不是新建。
> 2. 归位时检查：标签全库统一写法（同一概念不出现大小写混用）；
>    双链 [[]] 指向的文件存在。
> 3. 运行 06_工具箱/知识库检查.py，修复报告的断链 / frontmatter / 同名冲突。
> 4. 状态维护：已完结的项目笔记 状态 改 归档 并移入 08_归档/，
>    文件头标注取代关系。
> 5. 输出一份本周归档清单（移动了哪些文件、合并了哪些、修了哪些错）。

## 写入权限分级（防腐化核心）

受对话细节影响的模型直接写全库是知识库腐化的首要来源，因此按角色限制写入范围：

| 角色 | 可写 | 禁止 |
| --- | --- | --- |
| DeepSeek Pro（日常） | `00_收件箱/`、`01_项目/` 的进度类笔记、草稿 | 直接新建 / 重写 `02_知识库/`、`09_排坑/`、`03_开发板芯片/` |
| Qwen Flash（日常） | `00_收件箱/` 内的正式笔记草稿、git commit | 一切归位判断、README 全文重写 |
| Qwen Max（每周） | 归位、合并、归档、状态关闭 | 高频改动 |
| 人 | README diff 终审、归位争议裁决 | — |

`02_知识库/` `09_排坑/` `03_开发板芯片/` 的落位只有两条合法路径：周归档由 Qwen Max 执行，或 DeepSeek Pro 提出方案经人确认后执行。

## 内容红线（任何模型写库前必须遵守）

1. **先搜后写**：新建笔记前先全库搜同主题；已有则编辑合并，禁止另起新篇（防重复滋生）。
2. **笔记必须可脱离对话独立阅读**：禁止「如上所述 / 刚才 / 我们之前」等上下文依赖表述。
3. **结论必须带来源**：官方文档 / 实测 / 推测三选一，推测必须显式标注，禁止把对话中的猜测写成事实。
4. **对话记录 ≠ 知识**：一次性调试细节进 `01_项目/` 进度笔记，只有可复用结论才进 `02_知识库/`。
5. **已有笔记只做增量编辑**，禁止整段重写式转述（好笔记会被越改越差）。
6. 整理完成后运行 `06_工具箱/知识库检查.py`，【4】建议项逐条处理；参考类档案（板卡 / 芯片档案）可保留「进行中」，但需在周归档时确认仍在使用。

## 边界与禁忌

- 日记字段缺失时下游写「无」而不是猜测补全。
- 原始日记不删除，只移入 `08_归档/`（保留可追溯性）。
