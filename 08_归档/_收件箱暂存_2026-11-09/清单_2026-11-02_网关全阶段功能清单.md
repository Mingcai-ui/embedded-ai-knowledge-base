# 网关全阶段功能清单 · 每个阶段做到什么程度

> 项目：[[Modbus边缘采集网关-主档卡]]
> 前置：[[清单_2026-10-30_网关底层四项]]（P0-A 施工细则）、[[清单_2026-10-30_P0学习内容与视频取舍]]（P0 学习深度）
> **本文不重复那两份的内容**，只解决三件事：全项目有哪些功能、每个功能做到什么程度、它消耗你哪篇笔记。

---

## 0. 为什么你"理不清知识怎么用"

不是知识不够，是**两套组织方式对不上**：

| | 你的知识库 | 你的项目 |
|---|---|---|
| 组织维度 | 按技术分篇（UART、环形缓冲、FreeRTOS…） | 按数据流分段（采→解→存→传） |
| 单位 | 一篇笔记 = 一个知识点 | 一个功能 = 一段代码 + 一个可测现象 |
| 用起来需要 | 一个"翻译层" | ← 缺的就是这个 |

**翻译规则**（本文的骨架）：每个功能必须能填满这四格，缺一格说明它还不该开始写。

```
功能编号 → 消耗哪篇笔记 → 产出什么代码/接口 → 用什么现象证明它成了
```

下面每个功能都按这个填。

## 1. 完成度三级（回答"做到什么程度"）

同一句话"做了 Modbus 轮询"，可以有三种成色。**每阶段必须标明目标级别，否则永远做不完**。

| 级别 | 定义 | 判定动作 | 论文/面试价值 |
|---|---|---|---|
| **L1 能跑** | 正常路径有输出，异常不管，代码可能是 AI 写的 | 演示一次成功 | 无。只能证明"跑通过" |
| **L2 能测** | 异常分支有处理，有量化数据或日志可复现 | 给出数字/曲线/截图 | 论文测试章素材 |
| **L3 能讲** | 白板能画结构，能答"如果参数取小了会怎样"这类反事实追问 | 关掉代码讲 5 分钟 | 面试防御力，**这才是简历上的东西** |

**分级纪律**：
- 核心一/核心二的技术硬核（3.5T、CRC、调度器、环形缓冲、Flash 策略）→ **必须 L3**
- 胶水代码、界面、CubeMX 初始化 → L1 即可，AI 可代写
- 夹在中间的（SPI 驱动、MQTT 客户端）→ L2
- 每阶段结束在 Git 打一个 tag。5 个 tag = 简历上"版本演进"的证据，顺手补掉画像短板 #5（Git）

## 2. 全景表

| 阶段 | 主题 | 功能数 | 终点一句话 | 目标级别 |
|---|---|---|---|---|
| **P0-A** | 底层四项（骨架/CRC/3.5T/解析状态机） | 已有清单 | 能对任意字节流判帧并解析 | 全部 L3 |
| **P0-B** | 单主单从联机 | 6 | 读到真实设备的一个寄存器 | 核心 L3 |
| **P0-C** | 端到端灰度切片 | 3 | 一条数据从从机走到云端 | L1→L2 |
| **P1** | 协议栈生产化 + 多从机 | 7 | 3 从机不丢帧、故障隔离 | 核心 L3 |
| **P2** | 离线缓存 + 掉电恢复 + 看门狗 | 7 | 断网掉电数据不丢 | 核心 L3 |
| **P3** | 上云 + 上位机 + 远程写 | 7 | 云端曲线 + 下发控制 | L2 |
| **P4** | K230 事件通道（可选） | 3 | 视觉告警上报 | L1 |

> **P0-C 是新增的**。原档卡没有这一段，但它解决你最大的心理问题：做到 P2 之前你手里没有一个"完整的东西"，只有互不相连的四项技术。先切一条最细的端到端（1 从机 → 1 条 MQTT），拿到闭环，再回头加厚。**先纵后横，不是先横后纵。**

## 3. P0-B · 单主单从联机

前置：P0-A 四项全过（当前 ②CRC 已过，①③④ 未过）。

| 编号 | 功能 | 做到什么程度（L2/L3 判据） | 消耗的笔记 | 产出 |
|---|---|---|---|---|
| F0.1 | MAX485 方向控制 | **L3**：讲清 DE 拉高的最早时刻、拉低必须等 TC 中断而非 TXE；上电默认低电平 | MAX485 手册（外部） | `RS485_Send()` 封装，内含方向切换 |
| F0.2 | 请求组帧 03 | **L3**：手写组帧，参数为(从机地址,起始地址,数量)；自带 CRC 追加 | [[UART自定义帧协议_接收状态机与防误识别]]（结构迁移） | `mb_build_read_holding_regs()` |
| F0.3 | 应答解析成结构体 | **L3**：输出 `{addr,func,byte_count,data[253],status}`，status 含 CRC_ERR/ADDR_MISMATCH/EXC_xx/TIMEOUT | 同上 | `mb_parse_response()` |
| F0.4 | 单次轮询（阻塞版） | **L2**：发→等→解析→打印，允许 HAL_Delay 占位 | — | `mb_poll_once(addr,reg,n)` |
| F0.5 | 异常路径三件套 | **L3**：CRC 错→丢弃+计数、地址不符→静默丢弃不算错、超时→重试 1 次 | J2 已答：CRC 错帧**不回**异常码 | 计数器 + 日志 |
| F0.6 | 与 Modbus Slave 互通 | **L2**：PC 端 Modbus Slave 模拟从机，板子读它；再用 Modbus Poll 反向验板子发出的帧格式 | — | 互通截图（答辩用） |

**P0-B 出门条件**：连续 100 次读取成功率 ≥99%，且有一次故意制造 CRC 错/超时的日志留证。

## 4. P0-C · 端到端灰度切片（新增，1～3 天，别做完美）

目的：**证明链路存在**，不证明链路可靠。允许全部用最脏的写法。

| 编号 | 功能 | 做到什么程度 | 说明 |
|---|---|---|---|
| F0.7 | ESP32 AT 联网 + 发一条 JSON | **L1** | 硬编码 Topic，手拼字符串，不做重连 |
| F0.8 | 数据模型定型 | **L2** | 一条记录长什么样，要在这里定死，P1/P2 全按它走：`{ts, addr, reg, val, q}` |
| F0.9 | 云端能看见 | **L1** | 任一 MQTT 客户端（MQTTX / 阿里云 / 巴法云）收到即算过 |

> 为什么值得插这一段：F0.8 的数据模型是后面 20 个功能的公共契约。你项目里"知识用不上"的另一半原因是**缺少定型的数据结构**——没有它，每个功能都是孤岛。**F0.8 必须手写，不许 AI 定。**

## 5. P1 · 协议栈生产化 + 多从机

前置：FreeRTOS 第 7 周（信号量/互斥量）至少要"会用"，否则 F1.3 写不下去。

| 编号 | 功能 | 做到什么程度 | 消耗的笔记 | 备注 |
|---|---|---|---|---|
| F1.1 | DMA Circular + IDLE 接收 | **L2** | [[UART空闲中断接收不定长数据_IT与DMA双方案]] | 已验证，直接搬 |
| F1.2 | 环形缓冲（SPSC 版）重构 | **L3** | [[环形缓冲区]] + [[FreeRTOS_中断管理与临界区]] | 必须手写判满/判空；overrun 时"丢新保旧"并计数 |
| F1.3 | 帧事件队列：ISR → 队列 → 解析任务 | **L2** | [[FreeRTOS_任务管理与消息队列]] + 信号量 | 3.5T 判定**不许**用软件定时器（tick 1ms 不够） |
| F1.4 | 轮询调度器 | **L3** | 本档卡核心一 | 从机表驱动：`{addr, start, count, timeout, retry, state}`；状态 OFFLINE 时跳过 |
| F1.5 | 超时预算计算 | **L3** | — | 单帧耗时=请求字节×11/bps + 周转 + 应答字节×11/bps + 2×3.5T；算出 3 从机@9600 的轮询周期上界，**论文第 1 项指标** |
| F1.6 | 故障隔离与自动恢复 | **L2** | — | 连续 N 次失败→OFFLINE→每 M 轮探测→恢复后重新纳入 |
| F1.7 | 统计计数器 | **L1** | — | 总帧/CRC错/超时/丢弃/overrun，串口定期打印 |

**P1 出门条件**（=论文第 2、3 项指标）：
- 24h 连续灌入丢帧率 = 0，附测试方法
- 缓冲深度 1K/4K/8K 三档丢帧率对比表
- 拔掉 1 台从机，其余两台的数据间隔不变（用时间戳证明，不是"看着还行"）

## 6. P2 · 离线缓存 + 掉电恢复 + 看门狗

| 编号 | 功能 | 做到什么程度 | 说明 |
|---|---|---|---|
| F2.1 | SPI + W25Q64 基础驱动 | **L2** | 读 JEDEC ID、读/写状态寄存器、页读 |
| F2.2 | 页写/扇区擦除封装 | **L3** | 跨页必须拆（256B 边界）；擦除前判空；擦除 4KB 约 45ms，**擦除时不许阻塞采集任务** |
| F2.3 | 记录格式 + 校验 | **L2** | `magic + seq + ts + addr + reg + len + payload + crc8`；seq 单调递增是断点续传的唯一依据 |
| F2.4 | 环形写指针 + 磨损控制 | **L3** | 按 4KB 扇区轮转，写满擦最旧；白板能画出"当前写指针 + 已上传指针"两个游标 |
| F2.5 | 上电扫描未上传区 | **L2** | 找最大的合法 seq，从它之后继续；校验不过的页跳过 |
| F2.6 | 掉电断页处理 | **L3** | 页写中途掉电 → 该页校验失败 → 整页作废，从下一个扇区继续；**验收要真拔电 20 次** |
| F2.7 | IWDG + 任务存活检测 | **L2** | 喂狗点放在哪个任务要想清楚；各任务心跳位图，任一任务超时→记录→复位 |

**P2 出门条件**：随机拔电 20 次数据恢复 100%；断网 1h（拔网线或停 MQTT）后补传完整率 100%。

> 陷阱预警：Flash 擦写和采集跑在不同任务，共享"写指针"。这是互斥量的第一个真实用武之地（画像里互斥量还在"在学"档）——**把这个点当成互斥量的学习载体**，比刷视频有效。

## 7. P3 · 上云 + 上位机 + 远程写

| 编号 | 功能 | 做到什么程度 | 说明 |
|---|---|---|---|
| F3.1 | 上行链路串口分配 | **L1** | USART2 已给 485，需另开 USART3 或换引脚；这是 PinMux 冲突，早排 |
| F3.2 | MQTT 客户端 | **L2** | CONNECT / keepalive / QoS1 + PUBACK 超时重发 / LWT 遗嘱 / 断线重连 |
| F3.3 | Topic 与 JSON | **L2** | `dev/{sn}/up`、`dev/{sn}/down`、`dev/{sn}/status`；序列化手写，别上全量 cJSON（20KB RAM 不够挥霍） |
| F3.4 | 补传优先级 | **L2** | 先发缓存（F2.5 断点）再发实时；限速避免把链路打满 |
| F3.5 | 下行 06/16 写入 | **L2** | 参数校验、寄存器范围检查、失败回执 |
| F3.6 | 上位机（曲线+历史） | **L1** | AI 可代写；重点是数据模型 F0.8 一致 |
| F3.7 | 端到端时延测量 | **L2** | 寄存器变化 → 云端可见 的时延分布；论文第 4 项指标 |

**P3 出门条件**：云端实时曲线 + 下发控制后实物动作（继电器/LED 亮度）+ 拔网 10min 插回自动补传。

**P4（可选，只在时间富余或竞赛需要时做）**：K230 事件帧接收 → 复用校赛帧协议 → 并入同一 MQTT 通道（F4.1~F4.3）。不做也不影响毕设完整性。

## 9. 当前落点与最近 6 个动作

**现在的位置**：P0-A 四项中 ②CRC 已过，①骨架 / ③3.5T / ④解析状态机 未过。硬件仍在途。

按"不需要板子先做"的原则排序：

| # | 动作 | 需要板子 | 目标级别 | 预计 |
|---|---|---|---|---|
| 1 | ④ 解析状态机：先白板画，再手写代码（不许 AI 先写） | 否 | L3 | 4 h |
| 2 | ③ 3.5T：Python 模拟字节流喂状态机，验边界（4.0ms 判 1 帧 / 4.1ms 判 2 帧） | 否 | L3 | 3 h |
| 3 | 三帧手算（请求/应答/异常）写纸上拍照存 assets | 否 | L3 | 1 h |
| 4 | ① 骨架：CubeMX 四项配置 + boot 日志 | **是** | L2 | 3 h |
| 5 | F0.1 MAX485 方向控制 + F0.2/F0.3 组帧解析上板 | **是** | L3 | 6 h |
| 6 | Git 建仓 + 第一个 tag `p0-baseline` | 否 | L1 | 1 h |

> 第 2 步值得单独强调：**在 PC 上用 Python 模拟字节流 + 时间戳喂你的状态机逻辑**，可以在没板子的情况下把 ③ 和 ④ 全部验完。这比等硬件到货快得多，而且测过的边界条件写进论文就是测试用例。
