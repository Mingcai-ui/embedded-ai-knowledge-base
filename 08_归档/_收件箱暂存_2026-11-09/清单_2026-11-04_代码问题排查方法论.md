# 代码问题排查方法论（软件层）

> 定位：给"现象出现后，第一反应是改代码，而不是先确认现状"的我（见 [[个人画像]] 短板、[[FreeRTOS_学习进度_2026-10-23]] 四节结论）。
> 与 [[清单_2026-11-04_硬件物理排查]] 互为表里：软件走不动了才轮到硬件；但"软件改了没反应"往往要回头验硬件。

---

## 0. 一条总原则（先背下来）

**先定位，后修改；一次只改一个变量。**

- 现象出现 → 不是"猜哪里错就改哪里"，而是"缩小范围到确凿的一行"。
- 每次只改一处，改完立刻验证。一次改三处，就算好了也不知道是哪处治好的——下次还会踩。
- 改之前先问一句：**我现在测的，是不是刚编译出来的东西？**（见 [[FreeRTOS_阶段一故障合集]] 坑5：源码 13:24、elf 却是前一天 20:47）

---

## 1. 分层定位法（核心流程）

从现象往内收，每层都先排除再深入：

| 层 | 问题 | 用什么工具/动作 | 命中就停，别往下钻 |
|---|---|---|---|
| L1 现象层 | 灯不亮/不闪/串口没数据/死机 | 眼睛 + 串口打印 + 万用表量电压 | 确认"现象是否真实" |
| L2 链路层 | 电到底通没通、固件到底烧没烧 | elf 时间戳、复位、万用表通断 | 排除"没上电/没烧进去" |
| L3 模块层 | 是这个外设/这个任务/这个库的问题？ | 注释掉其他模块、最小工程 | 二分法缩小 |
| L4 函数层 | 是这个函数？ | 断点 + 单步 + Watch | 定位到函数 |
| L5 行层 | 是哪一行？ | F10 逐步 + 寄存器观察 | 定位到行 |

**铁律**：L1~L2 不确认，L5 的单步全是浪费。绝大多数"诡异 bug"卡在 L2（测的是旧固件）。

---

## 2. 二分法 / 最小复现（缩小范围的两把刀）

### 2.1 二分法

- 把"能跑"和"不能跑"之间的代码砍一半，看故障在哪一半。
- 方法：注释掉怀疑区间的一半 → 重编译 → 看现象。
- 适用：**改动后新出的 bug**（你知道"之前是好的"，只在这段 diff 里）。

### 2.2 最小复现工程

- 项目里其它模块全注释，只留出问题的模块 + 最小驱动。
- 适用：**新模块从一开始就不工作**，不知道是模块本身还是被别的干扰。
- 最小工程能复现 → 问题在模块内；不能复现 → 问题在模块间的交互（时序/资源/内存）。

---

## 3. 常见故障类型 → 对应排查入口（速查）

| 症状 | 大概率类型 | 第一个动作 |
|---|---|---|
| 突然 HardFault / 卡死 | 内存越界 / 野指针 / 栈溢出 | 看 HardFault 定位（§5） |
| 灯不闪但串口通 | 高优先级任务饿死 / 阻塞点缺失 | 查任务循环有无 `osDelay`（[[FreeRTOS_阶段一故障合集]] 坑1） |
| 数值不变 / 对不上 | 类型不匹配 / 字节截断 / 字节序 | 查 `sizeof`、队列 Item Size、类型（坑4、E01） |
| 改了没反应 | 测的旧固件 / 配置没重新生成 | 看 elf 时间戳、CubeMX 重新生成（坑5、坑8） |
| 中断不触发 | 没 `Start_IT` / 没使能 / 优先级 | 查 `HAL_xxx_Start_IT`、NVIC（坑7） |
| 偶发丢数据 | 时序 / 竞态 / 缓冲区溢出 | 逻辑分析仪 + 加大缓冲 + 打印计数 |
| 上电偶发失败 | 初始化顺序 / 未清零 / 未判空 | 逐条检查 init 返回值与顺序 |

## 4. 调试器完整用法（补齐画像短板 #8）

> 现状：断点/F5/F11/调用栈/局部变量已会；**Watch / Peripherals / Memory / Disassembly 四块面板一次没开过**。这四块是"从能用调试器"到"会定位"的分水岭。

### 4.1 Watch（表达式观察）

- 加表达式：`pxCurrentTCB->pcTaskName`、`uxCriticalNesting`、`uwTick`、`xPortGetFreeHeapSize()`。
- 用途：**看一个变量在运行中怎么变**，尤其"改了却没生效"时。
- 技巧：变量是快照，寄存器是实时值。停进 HAL 函数时局部变量是进函数瞬间的快照，标志位是否真的置上/清掉要看寄存器，不能只看变量（[[EIDE_JLink_调试环境搭建]] §6）。

### 4.2 Peripherals（外设寄存器）

- 打开：TIM 的 `SR`/`DIER`、NVIC 的 `ISER`/`SHPR`、SCB 的 `ICSR`/`BASEPRI`、GPIO 的 `IDR`/`ODR`。
- 用途：**外设到底配没配成、中断标志到底置没置**。比代码里 `if(flag)` 更接近真相。
- 典型场景："我明明写了 `Start_IT`，中断就是不触发" → 看 `DIER.UIE` 和 `SR.UIF` 位。

### 4.3 Memory（内存视图）

- 用途：看缓冲区实际字节、看结构体布局、查越界/覆盖。
- 典型场景：队列收发数据对不上 → 直接看内存里那段字节是什么。

### 4.4 Disassembly / 调用栈

- 调用栈：HardFault 后看"死在哪条调用链上"。
- 反汇编：`<optimized out>` 时、或怀疑编译器优化时看实际指令。

### 4.5 单步纪律（肌肉记忆）

- **F10 是默认键**（90% 场景），F11 只在"明确要看库内部"时按，Shift+F11 脱身。
- 首次实操曾拿 F11 当走一步，钻了五层库函数（[[EIDE_JLink_调试环境搭建]] §4）。

## 5. HardFault 定位（STM32 必会，最高频的"死机"）

### 5.1 为什么进 HardFault

- 访问非法地址（空指针、野指针、数组越界）
- 除以零（整数除零在某些配置下）
- 未对齐访问
- 栈溢出（任务栈配太小，FreeRTOS 尤其常见）
- 执行非法指令 / 跳到非法地址（函数指针野了）

### 5.2 定位三步

1. **看调用栈**：调试器停在 `HardFault_Handler` 里，往上翻调用栈，最靠近崩溃的那帧就是第一嫌疑。
2. **读 Fault 状态寄存器**（Cortex-M3/M4 都有）：
   - `SCB->CFSR`（Configurable Fault Status Register）分三段：
     - Bits [15:8] `BFARVALID`/`STKERR`/`UNSTKERR`/`IMPRECISERR`/`PRECISERR`/`IBUSERR`（BusFault）
     - Bits [7:0] `UNDEFINSTR`/`INVSTATE`/`INVPC`/`NOCP`/`UNALIGNED`/`DIVBYZERO`（UsageFault）
     - Bits [31:16] `MSTKERR`/`MUNSTKERR`/`DACCVIOL`/`IACCVIOL`（MemManage）
   - `SCB->BFAR`：BusFault 地址（PRECISERR 时有效，指向非法地址）。
   - `SCB->HFSR`：`FORCED` 位表示"被上级 fault 强制升级"。
3. **定位到行**：在调试控制台 `p/x SCB->CFSR`、`p/x SCB->BFAR`、`p/x SCB->HFSR`。

### 5.3 快速判别表

| CFSR 关键位 | 含义 | 最可能原因 |
|---|---|---|
| `INVPC` | 跳到了非法 PC | 函数指针野、返回地址被覆盖 |
| `UNALIGNED` | 非对齐访问 | 结构体指针强转错位、`packed` 后取多字节 |
| `IACCVIOL` | 取指越界 | 跳过了没代码的地址 |
| `DACCVIOL` + BFAR | 数据访问越界 | 数组越界、野指针、访问已释放内存 |
| `MSTKERR`/`STKERR` | 栈错误 | 栈溢出 / 栈指针被破坏 |

### 5.4 栈溢出专治（FreeRTOS）

- 排查手段：打开 `configCHECK_FOR_STACK_OVERFLOW`（设 2），再挂 `vApplicationStackOverflowHook` 断点。
- 运行时观测：`uxTaskGetStackHighWaterMark(task)` 看剩余栈水位，接近 0 就是危险。

## 6. printf / 日志调试（无调试器时的兜底）

| 手段 | 适用 | 注意 |
|---|---|---|
| printf 插桩 | 快速定位"走没走到这行、值是多少" | 会引入时序变化，可能掩盖竞态 bug；用完删 |
| 计数器打印 | 看丢包率/调用次数 | 比"打不打印"更定量 |
| LED 心跳 | 看任务是否还活着（饿死/卡死） | 最原始但最可靠，没有 UART 也能用 |
| 状态机日志 | 打印状态转移 + 时间戳 | 协议类 bug 首选 |

> 原则：**先用 printf 圈出范围，再用调试器精确定位**。printf 定位"大概在哪"，调试器定位"就是这一行"。

---

## 7. 时序类 bug（竞态/丢包/偶发）的排查顺序

这类 bug 用普通断点会"一停就正常"（Heisenbug），要用别的办法：

1. **逻辑分析仪**抓 IO/总线波形（见物理排查篇）。
2. **计数 + 时间戳打印**：不要打内容，打"第几次、什么时刻"。
3. **最小化 + 复现率统计**：先量化"多少次里出一次错"。
4. **关优化（-O0）复测**：排除编译器重排/优化干扰。
5. **怀疑竞态就加锁/关中断对照**：单开/双开对照实验。

---

## 8. 排查清单（出现 bug 时逐条过）

```
□ 1. 现象是什么？一次性能稳定复现吗？（不能 → 量化复现率，见 §7）
□ 2. 测的是不是最新固件？（elf 时间戳）
□ 3. 供电/复位/接线对不对？（先看物理篇）
□ 4. 缩小范围：注释一半 / 最小工程
□ 5. 定位到函数、到行（断点 + F10）
□ 6. 看 Watch 值 + Peripherals 寄存器
□ 7. 找到根因 → 改一处 → 验证
□ 8. 记进 [[清单_2026-11-02_错误记录总表]]，判断根因属于哪个模式（M1~M4）
```
