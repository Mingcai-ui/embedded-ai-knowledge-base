# FreeRTOS 阶段一：十个真实故障合集

> 环境：STM32F103C8T6 / HAL / FreeRTOS 10.3.1（CMSIS-OS2）/ CubeMX + VS Code + EIDE
> 来源：1~6 来自 [[FreeRTOS_学习进度_2026-10-23]] 阶段一（任务挂起恢复 + 消息队列）；7~10 来自中断管理与临界区一轮（2026-10-24~25，UART_Task 工程，见 [[FreeRTOS_学习进度_2026-10-24]]）。
> 与速查表第 13 章「通用 12 个坑」的区别：这 10 个是我本人踩的，带具体表现和修正动作。

## 1. 高优先级任务无阻塞 → 全系统饿死

**现象**：所有 LED 突然定格不闪，看起来像死机，但串口还能通。

**原因**：高优先级任务循环里没有 `osDelay` 或任何阻塞调用，一直占着 CPU。同优先级/低优先级任务永远轮不到。

**解决**：任何任务循环必须有阻塞点。不是"死机"，是饿死——别去查 HardFault。

**预防**：写完任务函数先扫一遍 `while(1)` 里有没有 `osDelay` / `osMessageQueueGet` / `osSemaphoreAcquire`。

## 2. 按住按键重复删除任务（句柄未置空）→ 断言死循环 / HardFault

**现象**：按键按住不放，系统进断言死循环或 HardFault。

**原因**：删除任务后没有把 `TaskHandle_t` 置 `NULL`，按住期间每次边沿都再 `vTaskDelete` 一次，操作已释放的 TCB。

**解决**：删除后立即 `handle = NULL`，下次删除前判空。

**预防**：按键处理必须"边沿触发 + 二次确认 + 等待松手"，每条分支都要有阻塞。

## 3. 用 `osThreadGetState` 判断是否被挂起 → 永远走 Resume 分支

**现象**：按键想切换挂起/恢复，按下去没反应（或只会恢复不会挂起）。

**原因**：`osThreadGetState` 把 `eBlocked` 和 `eSuspended` 合并返回 `osThreadBlocked`，区分不了"被挂起"和"在等队列/延时"。所以永远判不出"当前是挂起状态"。

**解决**：自己维护一个 `paused` 意图变量，用变量决定动作，不用状态查询倒推意图。

**预防**：RTOS 里"状态查询"和"意图"是两回事。要做什么，用自己记的标志；内核状态只用来观测。

## 4. 队列 Item Size 写成 `uint8_t`，代码按 `uint32_t` 收发 → 静默截断

**现象**：改队列里的模式号，LED 闪烁频率完全不变，代码看着没错。

**原因**：CubeMX 里 `Item Size` 填的 1 字节，代码按 4 字节 `uint32_t` 收发。队列按字节 `memcpy`，多出的 3 字节被丢掉，`switch` 永不命中。**不报错、不警告。**

**解决**：`typedef` 一个消息类型（如 `LEDMsg_t`），CubeMX 的 Item Size 直接填该类型大小，并加 `_Static_assert(sizeof(LEDMsg_t) == ITEM_SIZE, "")` 做编译期校验。

**预防**：队列的 `uxItemSize` 是唯一真相，传什么类型的指针内核都不检查。

## 5. 改完没编译 → 测的是昨天的固件

**现象**：改了半天代码，现象一点没变，越改越怀疑人生。

**原因**：EIDE 没有真正重新编译（或编译失败被忽略），烧进去的还是旧 `.elf`（曾出现源码 13:24、elf 却是前一天 20:47）。

**解决**：每次改动先确认 `build/Debug/*.elf` 时间戳变了，再看现象。

**预防**：把"看 elf 时间戳"变成动手第一步，而不是最后一步。

## 6. `FootprintOK = false` → 堆不够但界面无红叉

**现象**：每次 CubeMX 生成代码都打一条 `[FREERTOS]` 警告，界面没有任何红色报错，运行起来偶发创建失败。

**原因**：堆（`configTOTAL_HEAP_SIZE`）不足以容纳 任务栈 + 队列 + 定时器 + TCB，CubeMX 只给终端警告。原配置 3072 太小，调到 10240 才够。

**解决**：按"任务栈（字×4）+ 队列（长度×(元素+开销)）+ 定时器 + 各 TCB"估算，留 30% 余量。

**预防**：生成后扫一眼终端有没有 `[FREERTOS]` 字样，别只看界面。运行期可用 `xPortGetFreeHeapSize()` 观测。

## 7. 只 `Init` 不 `Start_IT` → 中断永不触发

**现象**：中断线、`extern`、回调全写对了，LED 就是不动。

**原因**：`MX_TIM1_Init` 只写寄存器配置，不置 `CR1.CEN`、不置 `DIER.UIE`。NVIC 通道由 `HAL_TIM_Base_MspInit` 使能了，但外设中断使能位和计数器启动要靠 `HAL_TIM_Base_Start_IT(&htim1)`。

**解决**：补一行 `HAL_TIM_Base_Start_IT(&htim1);`。

**预防**：中断不触发时排查顺序——先确认 `HAL_TIM_Base_Start_IT` 在不在 → 再算 ARR 是否合理 → 再怀疑中断优先级。

## 8. ARR 用了默认 65535 → 6.55s 才翻一次，误判"没烧进去"

**现象**：加了启动还是"不闪"（实际 6.55s 翻一次，观察窗口内看不到），一度怀疑代码没烧进去。

**原因**：72MHz ÷ 7200 ÷ 65536 = 6.55s 才翻转一次。且 CubeMX 里 Period 已改 9999 但生成代码还是 65535——三真相源不一致（改了 CubeMX 没重新生成）。

**解决**：ARR 改 9999 → 1s；CubeMX 改完必须重新生成，或手动同步 `tim.c`。

**预防**：看到"没反应"先算周期 `T = (PSC+1)×(ARR+1)/72MHz`，再怀疑烧录。

## 9. `HAL_Delay` 夹在关中断里 → 永久死锁

**现象**：关中断后 LED **永久**停，不是 5 秒后恢复。

**原因**：`HAL_Delay` 忙等 `uwTick` 变量 → `uwTick` 靠 TIM4 中断（prio 15）递增 → 被 BASEPRI=0x50 屏蔽 → `uwTick` 永久冻结 → `while` 死循环 → `portENABLE_INTERRUPTS()` 永不执行。

**解决**：改用轮询 `SysTick->VAL` 的 `delay_us_noint()`（关中断照跑，含回绕补偿）；更正确的做法是临界区里不放任何延时。

**预防**：记忆锚点——**"等变量"依赖中断，"查硬件计数器"不依赖**。临界区里 `osDelay` / `HAL_Delay` / 自写轮询 Delay 一律不许有。

## 10. 以为 `portDISABLE_INTERRUPTS()` 是"关全部中断"

**现象**：无法解释为什么正点原子教程里同样的代码能跑、自己工程里表现不同。

**原因**：它实质是 `msr basepri, 0x50`，只屏蔽 prio ≥ 5，prio 0~4 照跑；且无嵌套计数，`ENABLE` 无条件写 0——嵌套调用等于失效（第二次关闭是空操作，第一次恢复就全开）。

**解决**：认清优先级数值语义；应用代码一律用 `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`（带 `uxCriticalNesting` 计数）。

**预防**：别把"关中断"记成非黑即白，先问"屏蔽到哪条优先级线"。
